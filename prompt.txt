Build an Android Real-Time Two-Way Voice Translator

1. Project Goal

Create a professional Android application that works as a real-time two-way voice translator.

The user selects two languages:

- Language 1
- Language 2

Example:

Arabic ⇄ Turkish

The application continuously listens to spoken conversation in either language, detects which selected language is being spoken, converts speech to text, translates it into the other selected language, and reads the translation aloud.

The primary use case is a conversation between two people who speak different languages.

Example:

Person A speaks Arabic:

«"السلام عليكم، أين أقرب محطة مترو؟"»

The application immediately displays:

Arabic: السلام عليكم، أين أقرب محطة مترو؟

Turkish: Merhaba, en yakın metro istasyonu nerede?

Then the Turkish translation is spoken using Text-to-Speech.

If Person B replies in Turkish:

«"En yakın metro istasyonu şu tarafta."»

The application should automatically recognize that Turkish is being spoken and translate it into Arabic:

Turkish: En yakın metro istasyonu şu tarafta.

Arabic: أقرب محطة مترو في هذا الاتجاه.

6. Automatic Two-Way Detection

This is one of the most important features.

The application should listen continuously during Conversation Mode.

It should determine whether the user is speaking:

- Language 1
- Language 2

Example:

Selected:

Arabic ⇄ Turkish

User speaks Arabic.

The application should:

1. Detect speech
2. Detect/identify Arabic
3. Convert Arabic speech to text
4. Translate Arabic → Turkish
5. Display both texts
6. Speak Turkish translation

Then the second person speaks Turkish.

The application should:

1. Detect speech
2. Detect/identify Turkish
3. Convert Turkish speech to text
4. Translate Turkish → Arabic
5. Display both texts
6. Speak Arabic translation

Avoid requiring the user to manually select the direction after every sentence.

7. Speech Recognition

Implement speech recognition using a reliable Android-compatible solution.

Preferred approach:

- Android SpeechRecognizer where appropriate
- Flutter plugin abstraction
- Streaming/partial recognition if supported

The architecture must allow replacing the speech recognition provider later.

Create an abstraction:

abstract class SpeechRecognitionService {
  Future<void> initialize();
  Stream<SpeechRecognitionResult> listen(String locale);
  Future<void> stop();
  Future<void> cancel();
}

Support:

- Partial results
- Final results
- Error handling
- Microphone permissions
- Recognition timeout
- Network errors
- No speech detected
- Unsupported language

Do not crash when speech recognition fails.

8. Translation Engine

Create a translation service abstraction.

abstract class TranslationService {
  Future<String> translate({
    required String text,
    required String sourceLanguage,
    required String targetLanguage,
  });
}

The first implementation should use a configurable translation API.

Do NOT hard-code API keys.

Use secure configuration.

Example:

TRANSLATION_API_URL
TRANSLATION_API_KEY

Keep the translation provider modular so the application can later support:

- Google Cloud Translation
- Microsoft Translator
- DeepL
- LibreTranslate
- AI/LLM translation
- Local/offline translation models

The UI must not depend directly on a specific provider.

14. Automatic Language Detection

Implement automatic language detection where technically possible.

The detection algorithm should only consider the two selected languages.

For example:

Selected:

Arabic + Turkish

The detector only needs to decide:

Arabic OR Turkish

Do not attempt to detect all supported languages simultaneously.

This improves speed and reliability.

If confidence is low:

- Do not immediately translate
- Continue listening briefly
- Use contextual information
- Prefer the previous speaker/language when appropriate

Expose a configurable confidence threshold.

---

15. Low Latency

Latency is extremely important.

Target:

Speech stops
↓
Final transcript
↓
Translation
↓
TTS

Target total latency:

Preferably under 2–3 seconds

Use:

- Streaming speech recognition when available
- Async processing
- Efficient HTTP requests
- Request cancellation
- Debouncing
- Partial transcript handling
- Caching where useful

Do not translate every partial word.

Translate only when a sentence/utterance is sufficiently complete.

---

16. Noise Handling

Implement basic conversation-friendly noise handling.

Support:

- Voice activity detection where available
- Silence detection
- Automatic end-of-sentence detection
- Ignore very short sounds
- Ignore empty transcripts
- Prevent translation loops

Avoid repeatedly translating the application's own TTS output.

The microphone/listening pipeline should pause or reduce recognition while TTS is speaking.

---

17. Prevent Translation Feedback Loop

This is critical.

When the application speaks the translated sentence:

The microphone may hear the application speaker.

The app must NOT translate its own voice back.

Implement:

1. Pause recognition during TTS
2. Resume recognition after TTS
3. Optional short delay after TTS
4. Audio focus management

---

18. Offline Support

The architecture must support offline operation in the future.

At minimum:

- Store language configuration locally
- Store conversation history locally
- Cache frequently used translations
- Detect internet availability
- Show clear offline status

If offline speech recognition / translation models are available on the device, allow them to be integrated through interfaces.

Do not falsely claim that translation works offline if the current provider requires internet.
